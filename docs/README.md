# 개발자 단어장 서비스 명세

## 1. 서비스 소개

이 서비스는 웹 개발을 공부하는 사람이 낯선 개발 용어를 검색하고, 쉬운 설명을 읽으며, 로그인 후 자신만의 메모와 AI 학습 기능을 사용할 수 있는 개발자 단어장입니다.

단어 이름, 직역 의미, 설명, 코드 예시는 공개 데이터입니다. 로그인하지 않은 이용자도 단어 목록, 검색 결과, 단어 상세 의미와 설명, 코드 예시를 볼 수 있습니다. 개인 메모, 새 단어 요청, 기존 단어 수정 요청은 로그인한 이용자만 사용할 수 있습니다.

서비스의 핵심 원칙은 다음과 같습니다.

- 단어장 데이터는 모든 이용자에게 공개합니다.
- 개인 메모는 작성한 이용자만 조회하고 수정할 수 있습니다.
- 일반 사용자는 단어를 직접 변경하지 않고 관리자에게 등록 또는 수정을 요청합니다.
- 관리자는 단어를 등록·수정·삭제하고 요청을 완료 또는 거절 처리합니다.
- 알림은 실시간으로 보내지 않고 마이페이지의 요청 상태 변화로 보여줍니다.

## 2. 이용자 역할과 접근 권한

서비스에서는 비로그인 이용자, 일반 사용자, 관리자를 구분합니다.

| 기능 | 비로그인 | 일반 사용자(`user`) | 관리자(`admin`) |
| --- | --- | --- | --- |
| 단어 목록·검색·상세 조회 | 가능 | 가능 | 가능 |
| 개인 메모 조회·작성·수정 | 불가능 | 본인 메모만 가능 | 제공하지 않음 |
| 관리자에게 새 단어 요청 | 로그인 모달 표시 | 가능 | 관리자 페이지에서 직접 등록 |
| AI 초안 등록 요청 | 로그인 모달 표시 | 가능 | 관리자 직접 등록 |
| AI 퀴즈 | 로그인 모달 표시 | 마이페이지에서 가능 | 제공하지 않음 |
| 기존 단어 수정 요청 | 불가능 | 가능 | 단어를 직접 수정 |
| 마이페이지 | 불가능 | 가능 | 관리자 페이지로 대체 |
| 단어 등록·수정·삭제 | 불가능 | 불가능 | 가능 |
| 요청 완료·거절 처리 | 불가능 | 불가능 | 가능 |

화면 상단의 버튼도 현재 로그인 상태에 따라 달라집니다.

| 상태 | 표시할 버튼 |
| --- | --- |
| 비로그인 | 로그인 |
| 일반 사용자 | 마이페이지, 로그아웃 |
| 관리자 | 관리자 페이지, 로그아웃 |

관리자도 일반 사용자와 같은 단어 목록과 상세 설명을 봅니다. 단어 상세 화면에서는 개인 메모 버튼 대신 단어 **수정**과 **삭제** 버튼을 사용합니다.

권한 검사는 버튼을 숨기는 것만으로 끝내지 않습니다. 모든 저장·수정·삭제 Server Action에서 Better Auth 세션과 역할을 다시 확인합니다.

## 3. 화면과 URL 구성

| 화면 | 권장 URL | 역할 |
| --- | --- | --- |
| 단어 목록과 검색 | `/` | 전체 단어 조회, 검색, 카테고리 필터 |
| 단어 상세 | `/words/[slug]` | 설명 조회, 개인 메모 또는 관리자 단어 관리 |
| 마이페이지 | `/mypage` | 일반 사용자의 요청 내역 조회와 AI 퀴즈 시작 |
| AI 퀴즈 | `/quiz` | 일반 사용자의 난이도 선택, 5문제 풀이, 결과 확인 |
| 관리자 페이지 | `/admin` | 요청 목록 조회와 새 단어 등록 |

로그인과 회원가입은 별도 페이지로 이동하지 않고 현재 화면 위에 표시하는 모달(Modal)로 구현합니다.

## 4. 단어 데이터

### 4.1 필드

| 필드 | 자료형 | 필수 | 설명 |
| --- | --- | --- | --- |
| `_id` | `ObjectId` | 자동 생성 | MongoDB가 만드는 단어 고유 ID |
| `name` | `String` | 필수 | 이용자에게 표시할 단어 이름 |
| `meaning` | `String` | 필수 | 영어 원어와 단어를 직역한 한국어 뜻 |
| `slug` | `String` | 필수 | 상세 주소와 중복 확인에 사용하는 고유한 값 |
| `description` | `String` | 필수 | 초보자가 이해할 수 있는 단어 설명 |
| `category` | `String` | 필수 | 단어의 대표 카테고리 하나 |
| `tags` | `String[]` | 선택 | 단어의 세부 특징을 나타내는 태그 목록 |
| `codeExample` | `String` | 필수 | 단어를 실제 코드에서 사용하는 짧은 예시 |
| `codeLanguage` | `String` | 필수 | 코드 예시의 언어를 나타내는 식별자 |
| `createdAt` | `Date` | 자동 생성 | 단어가 처음 등록된 시각 |
| `updatedAt` | `Date` | 자동 생성 | 단어가 마지막으로 수정된 시각 |

단어 하나는 다음과 같은 형태입니다.

```js
{
  name: "HTTP",
  meaning: "Hypertext Transfer Protocol : 하이퍼텍스트 전송 규약",
  slug: "http",
  description:
    "웹에서 브라우저와 서버가 요청과 응답을 주고받을 때 사용하는 통신 규칙입니다.",
  category: "웹 기초",
  tags: ["통신", "요청과 응답"],
  codeExample: `const response = await fetch("/api/words");
const words = await response.json();

console.log(words);`,
  codeLanguage: "javascript",
  createdAt: new Date(),
  updatedAt: new Date(),
}
```

### 4.2 직역 의미

`meaning`에는 기술 용어의 영어 원어와 직역한 한국어 뜻을 `영어 원어 : 한국어 뜻` 형식으로 저장합니다. 화면 이름이 한글인 단어도 영어 원어를 함께 기록합니다.

```js
{
  name: "브랜치",
  meaning: "branch : 나무의 가지",
}
```

약어는 가능한 경우 전체 영어 이름을 사용합니다.

```js
{
  name: "HTTP",
  meaning: "Hypertext Transfer Protocol : 하이퍼텍스트 전송 규약",
}
```

`meaning`은 Markdown 기호를 넣지 않은 일반 문자열로 저장하며, 현재 검색 대상에는 포함하지 않습니다.

### 4.3 카테고리와 태그

단어 하나에는 카테고리를 하나만 지정합니다. 처음 사용하는 카테고리는 다음 6개입니다.

1. 웹 기초
2. React
3. 데이터
4. Next.js
5. JavaScript
6. 기타

단어의 대표 분야를 알기 어렵다면 `기타`를 선택합니다. 태그는 선택 항목이며 여러 개를 지정할 수 있습니다. 태그가 없으면 빈 배열 `[]`로 저장합니다.

관리자 입력 화면에서는 태그를 쉼표로 구분해 작성합니다.

```text
통신, 요청과 응답, 웹
```

저장하기 전 앞뒤 공백을 제거하고 다음 배열로 변환합니다.

```js
["통신", "요청과 응답", "웹"]
```

### 4.4 슬러그

슬러그(Slug)는 단어 상세 주소의 마지막 부분입니다.

```text
/words/http
       └── HTTP 단어의 slug
```

슬러그는 영문 소문자, 숫자, 하이픈(`-`)만 사용하고 단어마다 고유해야 합니다. Seed 스크립트도 `slug`를 기준으로 이미 존재하는 단어인지 확인합니다.

### 4.5 코드 예시와 언어

모든 단어에는 설명과 함께 짧은 코드 예시를 저장합니다. `codeExample`에는 Markdown 코드 블록 기호 없이 코드 내용만 문자열로 저장하고, 화면에서 `<pre><code>` 요소로 표시합니다. 이렇게 하면 데이터와 화면 표현을 분리할 수 있습니다.

`codeLanguage`는 다음 네 값 중 하나만 사용합니다.

| 저장 값 | 화면 표시 | 사용 예 |
| --- | --- | --- |
| `javascript` | JavaScript | 일반 JavaScript, Node.js, MongoDB, Server Action |
| `jsx` | JSX | React 컴포넌트와 Next.js 화면 예시 |
| `bash` | Bash | Git과 터미널 명령 |
| `text` | Text | 폴더 구조처럼 실행 언어가 없는 예시 |

언어 이름을 제한하면 잘못된 철자나 서로 다른 표기(`js`, `JavaScript`, `javascript`)가 섞이는 것을 막고, 추후 syntax highlighting을 추가할 때 같은 값을 그대로 사용할 수 있습니다. 현재 검색 범위는 기존 규칙대로 `name`과 `description`이며 직역 의미와 코드 예시는 검색 대상에 포함하지 않습니다.

## 5. 검색

검색어가 단어의 `name` 또는 `description`에 포함되어 있으면 결과에 표시합니다.

- 부분 일치 검색을 사용합니다.
- 영문 대소문자를 구분하지 않습니다.
- 검색어의 앞뒤 공백은 제거합니다.
- 카테고리 필터와 검색어를 함께 사용할 수 있습니다.
- 검색과 카테고리는 Query String으로 관리합니다.

예를 들어 `요청`을 검색하면 설명에 해당 표현이 들어 있는 HTTP가 결과에 포함될 수 있습니다.

```text
/?query=요청&category=웹%20기초
```

검색 결과가 없으면 **단어 등록 요청** 버튼 하나를 표시합니다. 비로그인 사용자는 로그인 모달로 안내하고, 일반 사용자는 요청할 단어를 확인하여 제출합니다.

요청은 먼저 `wordRequests`에 저장합니다. AI가 기존 단어 필드 구조로 초안을 작성하고, 관리자는 상단의 신규 등록 요청에서 내용을 검토합니다. 승인 전에는 `words`에 저장하지 않으며 공개 검색 결과에도 나타나지 않습니다.

AI 생성 실패 또는 생성 제한으로 초안을 만들지 못한 경우에도 요청을 보존하고 **자동생성 실패. 관리자 확인요망**을 표시합니다. 관리자가 직접 내용을 작성할 수 있습니다.

## 6. 로그인과 회원가입

로그인과 회원가입은 Better Auth의 이메일·비밀번호 인증을 사용합니다.

### 6.1 로그인 모달

로그인 모달에는 다음 요소를 표시합니다.

- 이메일 입력
- 비밀번호 입력
- 로그인 버튼
- 회원가입 화면으로 전환하는 버튼
- 모달 닫기 버튼

이메일이 없거나 비밀번호가 틀린 경우를 구분하지 않고 다음 메시지 하나를 사용합니다.

```text
이메일 또는 비밀번호를 확인해 주세요.
```

로그인에 성공하면 모달을 닫고 현재 페이지를 새로고침하여 로그인 상태에 맞는 기능을 표시합니다.

### 6.2 회원가입

회원가입 화면에는 이용자가 입력하는 이메일과 비밀번호만 표시합니다. Better Auth가 내부적으로 요구하는 사용자 이름은 서버에서 이메일을 바탕으로 만들어 전달합니다.

- 이메일은 올바른 이메일 형식이어야 합니다.
- 비밀번호는 최소 4자입니다.
- 영문·숫자·특수문자의 조합은 강제하지 않습니다.
- 이미 가입된 이메일은 다시 사용할 수 없습니다.

회원가입 성공 시 자동 로그인한 뒤 현재 주소를 유지한 채 새로고침합니다. 단어 상세 화면에서 가입했다면 같은 단어 상세 화면에 남아 바로 메모 기능을 사용할 수 있습니다.

### 6.3 로그아웃

로그아웃하면 Better Auth 세션을 종료한 뒤 현재 주소를 유지한 채 새로고침합니다. 개인 메모 데이터는 삭제하지 않으며, 다시 로그인하면 확인할 수 있습니다.

## 7. 개인 메모

개인 메모는 로그인한 일반 사용자만 사용할 수 있습니다. 같은 단어라도 사용자마다 서로 다른 메모를 가집니다. 다른 사용자의 메모는 조회하거나 수정할 수 없습니다.

### 7.1 데이터 구조

| 필드 | 자료형 | 설명 |
| --- | --- | --- |
| `_id` | `ObjectId` | 메모 고유 ID |
| `userId` | `String` | Better Auth 사용자 ID |
| `wordId` | `String` | 메모가 속한 단어 ID |
| `content` | `String` | 사용자가 작성한 개인 메모 |
| `createdAt` | `Date` | 최초 작성 시각 |
| `updatedAt` | `Date` | 마지막 수정 시각 |

한 사용자는 같은 단어에 메모를 하나만 작성할 수 있습니다. 따라서 `userId + wordId` 조합은 고유해야 합니다.

### 7.2 화면 동작

해당 단어에 메모가 없을 때 별도의 안내 문구는 표시하지 않고 **메모하기** 버튼만 보여줍니다.

1. 메모하기를 누르면 단어 상세 화면의 버튼 아래에 입력 영역이 펼쳐집니다.
2. 저장을 누르면 “메모를 저장하시겠습니까?” 확인창을 표시합니다.
3. 확인창에서 취소하면 입력 내용을 유지합니다.
4. 확인을 누르면 실제 저장을 실행합니다.
5. 성공하면 “메모가 저장되었습니다.”를 표시하고 입력창을 닫습니다.
6. 저장된 메모, 작성 시각, 수정 시각, 수정 버튼을 같은 위치에 표시합니다.

기존 메모를 수정할 때는 기존 내용을 입력창에 채웁니다. 수정 성공 시 “메모가 수정되었습니다.”를 표시합니다. 입력 영역의 취소 버튼은 변경 내용을 버리고 원래 메모 보기로 돌아갑니다.

메모 삭제 시 화면은 **메모하기** 버튼만 있는 초기 상태로 돌아갑니다. DB 문서는 삭제하지 않습니다. `deletedAt`으로 삭제 상태를 기록하고 `history` 배열에 등록·수정·삭제 당시의 내용과 시각을 보존합니다. 재등록해도 이전 이력은 유지됩니다. 삭제된 내용과 이력은 일반 화면으로 전달하지 않습니다.

`history` 항목은 `{ type: "created" | "updated" | "deleted", content, createdAt }` 구조입니다. 이전 버전에서 작성한 메모는 현재 남아 있는 내용과 등록·최종 수정 시각을 이력에 보충합니다. 이전 버전이 보관하지 않았던 과거 수정 내용은 복원할 수 없습니다.

메모가 비어 있거나 공백만 있으면 다음 오류를 표시합니다.

```text
메모 내용을 입력해 주세요.
```

## 8. 새 단어 요청

검색 결과가 없을 때 로그인한 사용자는 관리자에게 새 단어 등록을 요청할 수 있습니다.

### 8.1 데이터 구조

| 필드 | 자료형 | 설명 |
| --- | --- | --- |
| `_id` | `ObjectId` | 요청 고유 ID |
| `userId` | `String` | 요청한 사용자 ID |
| `requestedWord` | `String` | 사용자가 요청한 현재 단어 이름 |
| `normalizedWord` | `String` | 중복 검사와 묶음 처리에 사용하는 정규화된 이름 |
| `status` | `String` | `pending`, `completed`, `rejected` 중 하나 |
| `wordId` | `String` 또는 없음 | 관리자가 등록한 단어 ID |
| `rejectionReason` | `String` 또는 없음 | 관리자가 작성한 거절 사유 |
| `createdAt` | `Date` | 최초 요청 시각 |
| `updatedAt` | `Date` | 요청 수정 또는 처리 시각 |

추가 필드는 `draft`와 `message`입니다. `draft`에는 `words`와 같은 이름의 콘텐츠 필드 8개를 보관하고, 생성 실패 시 `null`입니다. `message`에는 관리자 검토 안내를 저장합니다. 요청 단어를 수정하면 기존 초안을 지우고 새 단어 기준으로 다시 생성합니다.

`normalizedWord`는 요청 단어의 앞뒤 공백을 제거하고 영문을 소문자로 바꾼 값입니다. 같은 사용자가 동일한 `normalizedWord`에 대해 가질 수 있는 `pending` 요청은 하나뿐입니다.

| 기존 상태 | 같은 단어 재요청 |
| --- | --- |
| `pending` | 불가능 |
| `completed` | 검색 결과에 단어가 나타나므로 요청 버튼 미표시 |
| `rejected` | 가능 |

거절 후 재요청하면 이전 데이터를 되돌리지 않고 새 요청을 만듭니다. 과거 거절 기록은 마이페이지에 그대로 남습니다.

### 8.2 사용자의 요청 수정

사용자는 `pending` 상태인 요청 단어의 오타를 수정할 수 있습니다. 요청 자체를 취소하거나 삭제할 수는 없습니다.

- 요청 수정 시 `requestedWord`와 `normalizedWord`를 함께 변경합니다.
- `createdAt`은 유지하고 `updatedAt`만 변경합니다.
- 이전 오타 내용은 별도로 보관하지 않습니다.
- 이미 같은 사용자의 동일한 `pending` 요청이 있으면 수정을 거절합니다.
- `completed` 또는 `rejected` 요청은 수정할 수 없습니다.

## 9. 기존 단어 수정 요청

로그인한 일반 사용자의 단어 상세 화면에는 **메모하기** 옆에 **수정 요청하기** 버튼을 표시합니다.

### 9.1 데이터 구조

| 필드 | 자료형 | 설명 |
| --- | --- | --- |
| `_id` | `ObjectId` | 수정 요청 고유 ID |
| `userId` | `String` | 요청한 사용자 ID |
| `wordId` | `String` | 수정 대상 단어 ID |
| `message` | `String` | 사용자가 작성한 자유 형식의 수정 의견 |
| `status` | `String` | `pending`, `completed`, `rejected` 중 하나 |
| `rejectionReason` | `String` 또는 없음 | 관리자가 작성한 거절 사유 |
| `createdAt` | `Date` | 최초 요청 시각 |
| `updatedAt` | `Date` | 요청 수정 또는 처리 시각 |

같은 사용자는 같은 단어에 `pending` 수정 요청을 하나만 가질 수 있습니다. 완료되거나 거절된 뒤에는 새 수정 요청을 보낼 수 있습니다.

### 9.2 작성 화면

수정 요청은 자유롭게 작성할 수 있는 `message` 입력창 하나만 사용합니다. `textarea`에는 다음 예시를 `placeholder`로 표시합니다.

```text
예시)
수정할 부분: 단어 설명
수정 이유: 현재 설명이 초보자가 이해하기 어렵습니다.
수정 제안: HTTP는 브라우저와 서버가 데이터를 주고받기 위한 약속입니다.
```

Placeholder는 안내일 뿐 DB에 저장되지 않습니다. 사용자가 실제로 입력한 내용만 `message`로 저장합니다. 빈 내용이나 공백만 입력하면 “수정 요청 내용을 입력해 주세요.”를 표시합니다.

사용자는 `pending` 요청의 `message`를 수정할 수 있지만 요청을 취소하거나 삭제할 수 없습니다. 수정 시 이전 내용은 보관하지 않고 현재 내용으로 덮어쓰며 `updatedAt`을 변경합니다.

## 10. 마이페이지

마이페이지는 일반 사용자가 본인의 요청 내역을 확인하고 AI 퀴즈를 시작하는 화면입니다. 실시간 알림, 읽음·안 읽음 상태, 별도의 알림 컬렉션은 현재 구현 범위에 포함하지 않습니다.

화면 상단에 **AI 퀴즈** 버튼을 표시하며, 버튼을 누르면 난이도를 선택하고 퀴즈를 시작할 수 있는 `/quiz`로 이동합니다.

요청 종류별로 두 개의 아코디언을 표시합니다.

```text
▼ 새 단어 요청 내역 2건
▶ 수정 요청 내역 3건
```

각 아코디언 안에서는 요청을 상태별로 다시 나누지 않고 최근 요청부터 하나의 목록으로 보여줍니다.

| 상태 | 화면 표시 |
| --- | --- |
| `pending` (검증 대기중) | 요청 내용, 요청일, 마지막 수정일, 요청 수정 버튼 |
| `completed` (처리완료) | 요청 내용, 요청일, 완료일, 대상 단어가 있으면 단어 보러 가기 버튼 |
| `rejected` (등록불가) | 요청 내용, 요청일, 거절 사유, 거절 처리일, 대상 단어가 있으면 단어 보러 가기 버튼 |

새 단어 요청이나 기존 단어 수정 요청의 `wordId`에 해당하는 단어가 현재 존재할 때만 **단어 보러 가기** 버튼을 표시합니다. 거절되어 단어가 생성되지 않았거나 관리자가 해당 단어를 삭제했다면 `삭제된 단어`라고 표시하고 상세 화면 이동 버튼은 숨깁니다. 요청 내용과 처리 상태는 과거 내역으로 계속 보여줍니다.

### 10.1 스크랩한 단어카드와 최근 본 단어카드

일반 사용자는 목록 카드와 상세 화면에서 즐겨찾기를 추가·해제합니다. 마이페이지의 **스크랩한 단어카드 · 목록보기**는 기본 접힘 상태이며 펼치면 최근 추가 순서로 표시합니다. 해제한 카드는 목록에서 사라집니다.

`favorites`: `_id`, `userId`, `wordId`, `createdAt`. 사용자·단어 조합을 고유하게 관리합니다.

상세 화면을 실제로 열면 최근 열람을 기록합니다. 같은 단어를 다시 열면 맨 위로 이동하고 중복 없이 최대 10개만 보관합니다. 링크 사전 로딩은 기록하지 않습니다. 각 항목의 × 버튼은 해당 항목만, **최근 기록 모두 삭제**는 해당 사용자 기록 전체를 삭제합니다.

`recentWords`: `_id`, `userId`, `words: [{ wordId, viewedAt }]`. 사용자별 한 문서에 최근순으로 최대 10개를 보관합니다. 다른 사용자의 기록은 조회·변경할 수 없습니다.

### 10.2 단어 공유

목록 카드의 **자세히보기** 버튼을 누르면 상세 화면으로 이동합니다. 공유 버튼은 상세 화면에서만 표시하며, 비로그인을 포함한 모든 이용자가 링크 복사와 카카오톡 공유를 선택할 수 있습니다. 공유 주소는 해당 단어의 상세 주소입니다.

카카오톡 공유는 공식 JavaScript SDK를 사용합니다. 다음 공개 환경변수를 설정한 뒤 다시 빌드하면 활성화됩니다. 미설정 시 버튼은 비활성화하고 준비 중 안내를 표시합니다.

- `NEXT_PUBLIC_KAKAO_JAVASCRIPT_KEY`: 카카오 앱의 JavaScript 키 (관리자 키나 REST API 키가 아님)
- `NEXT_PUBLIC_SITE_URL`: 공유할 공개 서비스의 원점 주소 (예: `https://example.com`)

카카오 개발자 콘솔에 JavaScript SDK 도메인 및 공유 링크 도메인을 등록해야 합니다. 개발용 localhost 주소는 외부 수신자가 접속할 수 없으므로 실제 카카오 공유 검증은 공개 도메인 준비 후 수행합니다.

## 11. 관리자 페이지

관리자 페이지 최상단에 **신규 등록 요청 · 검증 대기중**을 펼쳐 표시합니다. **이전 등록 요청 내역**, **등록된 단어 관리**, **기존 단어 수정 요청**도 제공합니다. 등록된 단어 목록에서 수정 화면으로 이동하거나 삭제할 수 있고 직접 신규 등록도 가능합니다. AI 퀴즈는 학습용 기능이므로 관리자 계정에는 제공하지 않습니다.

두 요청 목록은 독립적으로 열고 닫을 수 있는 아코디언입니다.

```text
▼ 새 단어 요청 3건
▶ 기존 단어 수정 요청 2건

[새 단어 등록]
```

### 11.1 새 단어 요청 처리

같은 `normalizedWord`의 `pending` 요청은 관리자 목록에서 묶어서 보여줍니다.

```text
웹소켓 · 요청 인원 3명

[단어 등록하기] [요청 거절하기]
```

AI 초안 카드와 **해당 카드를 등록할까요?** 문구를 표시합니다. **초안 검토·승인**을 누르면 기존 필드 이름을 그대로 사용하는 입력 폼에 초안을 채웁니다. 관리자는 필요한 내용을 수정한 뒤 저장·확인하여 공개합니다. 초안 생성에 실패하면 **자동생성 실패. 관리자 확인요망**과 직접 작성·등록 기능을 제공합니다.

- 저장 후 확인을 눌러야 실제 등록을 실행합니다.
- 입력 영역에서 취소하면 입력 내용을 버리고 영역을 닫습니다.
- 등록 성공 시 같은 단어의 모든 `pending` 요청을 `completed`로 변경합니다.
- 각 요청에 생성된 단어의 `wordId`를 저장합니다.
- 각 요청의 `updatedAt`을 등록 완료 시각으로 변경합니다.
- 처리 후 관리자 페이지로 돌아와 목록을 다시 조회합니다.

등록불가 처리를 누르면 필수 사유 입력창을 표시합니다. “현재 등록 중인 단어입니다.”는 예시 문구이며 실제 입력값만 저장합니다. 거절 사유는 필수이며 저장·확인 후 같은 단어의 모든 `pending` 요청을 같은 사유로 `rejected` 처리합니다.

```text
예시)
요청하신 단어가 이미 다른 이름으로 등록되어 있습니다.
기존 단어를 확인해 주세요.
```

### 11.2 수정 요청 처리

수정 요청은 같은 단어에 여러 건이 있어도 하나로 합치지 않습니다. 내용이 서로 다를 수 있기 때문에 관리자가 선택한 요청을 각각 처리합니다.

관리자가 **단어 수정하기**를 누르면 해당 단어 상세 화면으로 이동하고 기존 정보가 입력 영역으로 바뀝니다. 저장 성공 시 선택한 수정 요청 하나만 `completed`로 변경합니다. 같은 단어의 나머지 요청은 `pending`을 유지합니다.

관리자가 요청 목록을 거치지 않고 상세 화면에서 직접 수정한 경우에는 단어만 변경하며 어떤 수정 요청도 완료 처리하지 않습니다.

요청 거절하기를 누르면 해당 요청 아래에 거절 사유 입력 영역을 표시합니다. 사유를 저장하고 확인하면 선택한 요청 하나만 `rejected`로 변경합니다.

## 12. 관리자 단어 등록·수정·삭제

### 12.1 등록과 수정

새 단어 등록 입력 항목은 다음과 같습니다.

- 단어 이름
- 단어 직역 의미
- 단어 설명
- 카테고리
- 태그
- 슬러그
- 코드 예시
- 코드 언어

관리자 단어 상세 화면에서 **수정**을 누르면 표시 중인 정보가 기존 값이 채워진 입력 영역으로 바뀝니다. 취소하면 변경 내용을 버리고 원래 상세 화면으로 돌아갑니다.

요청을 통해 들어온 수정에 성공하면 관리자 페이지의 수정 요청 목록으로 돌아갑니다. 단어 상세 화면에서 직접 수정한 경우에는 현재 상세 화면에 머뭅니다.

### 12.2 단어만 하드 삭제

삭제는 `words` 컬렉션에서 선택한 단어 문서 하나만 제거하는 하드 삭제(Hard Delete)로 처리합니다. 삭제 전에 등록·수정 이력을 `wordHistory`에 보관하고 단어 원본만 삭제합니다. 이력 보관에 실패하면 삭제하지 않습니다.

단어와 연결된 다음 데이터는 삭제하거나 수정하지 않고 기존 상태 그대로 보관합니다.

- 사용자가 작성한 개인 메모
- 해당 단어에 대한 기존 수정 요청
- 해당 단어의 `wordId`가 연결된 새 단어 요청 내역
- 사용자 계정과 다른 단어 데이터

삭제된 단어의 상세 주소로 접근하면 찾을 수 없음 화면을 표시합니다. 마이페이지와 관리자 페이지에서는 남아 있는 요청 내역을 계속 보여주되, 대상 단어를 찾을 수 없으면 `삭제된 단어`라고 표시하고 **단어 보러 가기** 또는 **단어 수정하기**처럼 단어가 필요한 버튼은 숨깁니다.

단어 원본은 삭제되며 관리자 이력에서 과거 내용을 확인할 수 있지만 복구 버튼은 제공하지 않습니다. 다음 확인창을 표시합니다.

```text
이 단어만 삭제되며 복구할 수 없습니다.
연결된 개인 메모와 요청 내역은 기록으로 남습니다.

삭제하시겠습니까?
```

삭제 Server Action에서는 관리자 세션과 역할, 단어 ID, 단어 존재 여부를 다시 확인합니다. 이력을 먼저 보관하고 조회 당시 수정 시각이 동일할 때만 `words` 원본을 삭제합니다. 삭제된 단어 문서는 남지 않으므로 `isDeleted`, `deletedAt`, 삭제 시점의 `updatedAt`도 저장하지 않습니다.

## 13. 저장·확인·취소와 결과 메시지

작성과 수정 기능은 공통으로 다음 순서를 따릅니다.

1. 사용자가 내용을 입력합니다.
2. **저장**을 누릅니다.
3. 확인창에서 **확인** 또는 **취소**를 선택합니다.
4. 확인을 누르면 서버 처리를 실행합니다.
5. 취소를 누르면 입력 내용을 유지한 채 작성·수정 화면으로 돌아갑니다.
6. 서버 처리 결과에 따라 성공 또는 오류 메시지를 표시합니다.

입력 영역 자체의 취소 버튼은 내용을 저장하지 않고 입력 영역을 닫습니다. 요청 내역의 **요청 수정** 화면에서 취소를 눌러도 요청 자체가 취소되는 것은 아닙니다.

처리 결과는 화면 상태에서 다음처럼 구분합니다.

```js
{
  type: "success",
  message: "메모가 저장되었습니다.",
}
```

```js
{
  type: "error",
  message: "메모를 저장하지 못했습니다. 잠시 후 다시 시도해 주세요.",
}
```

수정 요청 데이터의 `message`는 사용자가 작성한 의견을 DB에 저장하는 필드입니다. 위 예시의 결과 `message`는 저장 처리의 성공 또는 실패를 잠시 화면에 알려주는 UI 상태입니다. 이름은 같지만 쓰임과 저장 위치가 다릅니다.

| 상황 | 메시지 |
| --- | --- |
| 새 메모 저장 성공 | 메모가 저장되었습니다. |
| 기존 메모 수정 성공 | 메모가 수정되었습니다. |
| 새 단어 요청 성공 | 단어 요청이 등록되었습니다. |
| 수정 요청 성공 | 수정 요청이 등록되었습니다. |
| 요청 내용 수정 성공 | 요청 내용이 수정되었습니다. |
| 관리자 단어 등록 성공 | 단어가 등록되었습니다. |
| 관리자 단어 수정 성공 | 단어가 수정되었습니다. |
| 관리자 단어 삭제 성공 | 단어가 삭제되었습니다. |
| 요청을 통한 단어 수정 성공 | 단어 수정과 요청 처리가 완료되었습니다. |
| 요청 거절 성공 | 요청이 거절되었습니다. |
| 관리자 권한 없음 | 관리자만 이용할 수 있는 기능입니다. |

## 14. 날짜와 시간 규칙

등록·수정·요청·요청 처리 데이터에는 `createdAt`과 `updatedAt`을 사용합니다.

- 새 데이터 생성 시 두 값은 같은 시각입니다.
- 실제 DB 데이터가 변경되었을 때만 `updatedAt`을 변경합니다.
- 입력창 열기, 취소, 검증 실패, 서버 처리 실패는 `updatedAt`을 변경하지 않습니다.
- 하드 삭제된 단어 문서는 남지 않으므로 삭제 시각을 기록하지 않습니다.
- 단어 삭제 시 관련 메모와 요청 내역은 수정하지 않으므로 해당 데이터의 `updatedAt`도 변경하지 않습니다.

화면에서는 상태에 따라 `updatedAt`을 마지막 수정일, 등록 완료일, 수정 완료일 또는 거절 처리일로 표현합니다.

## 15. 초기 데이터(Seed Data)

`scripts/seeds.js`는 개발 환경에 다음 데이터를 준비합니다.

| 데이터 | 개수 | 중복 확인 기준 |
| --- | ---: | --- |
| 단어 | 30개 | `slug` |
| 테스트 사용자 | 3명 | `email` |
| 개인 메모 | 3개 | `userId + wordId` |

새 단어 요청과 수정 요청은 초기 데이터에 넣지 않습니다. 실제 기능을 사용하며 생성합니다.

Seed는 다음 순서로 실행합니다.

1. Better Auth로 테스트 사용자를 생성하고 사용자 ID를 확인합니다.
2. 카테고리별 단어, 직역 의미, 코드 예시를 저장하고 단어 ID를 확인합니다.
3. 사용자 ID와 단어 ID를 연결해 개인 메모를 저장합니다.

30개 초기 단어에는 모두 `meaning`, `codeExample`, `codeLanguage`가 들어 있습니다. 기존 단어에서 `meaning`이나 코드 필드가 없거나 값이 올바르지 않을 때만 해당 필드를 Seed 값으로 보충하고 `updatedAt`을 보충 시각으로 변경합니다. 이미 유효한 직역 의미와 코드 예시를 비롯해 이름, 설명, 카테고리, 태그 등 사용자가 수정한 값은 덮어쓰지 않습니다.

스크립트를 다시 실행해도 없는 사용자, 단어, 메모만 추가하며 유효한 기존 데이터는 유지합니다. 따라서 사용자가 변경한 비밀번호, 개인 메모, 직역 의미, 코드 예시를 Seed 데이터로 되돌리지 않습니다.

### 15.1 테스트 계정

아래 계정은 개발 환경에서만 사용합니다.

| 이메일 | 비밀번호 | 역할 | 초기 메모 |
| --- | --- | --- | --- |
| `learner1@example.com` | `DevStudy1!Pass` | `admin` | HTTP |
| `learner2@example.com` | `DevStudy2!Pass` | `user` | useState |
| `learner3@example.com` | `DevStudy3!Pass` | `user` | 배열 |

첫 번째 사용자는 관리자이며, 나머지 두 사용자는 일반 사용자입니다. 비밀번호는 Better Auth API를 통해 해시된 후 `account` 컬렉션에 저장합니다. 원문 비밀번호를 직접 DB에 저장하지 않습니다.

관리자 계정의 HTTP 메모도 사용자·단어 연결을 검증하기 위한 초기 데이터로 저장됩니다. 현재 화면 명세에서는 관리자에게 개인 메모 UI를 표시하지 않으므로 이 메모는 관리자 화면에 노출되지 않습니다.

### 15.2 실행 환경

루트의 `.env.local`에 다음 환경 변수가 필요합니다.

```dotenv
MONGODB_URI=mongodb://127.0.0.1:27017
MONGODB_DB_NAME=dev-words
BETTER_AUTH_SECRET=32자 이상의 충분히 긴 임의 문자열
BETTER_AUTH_URL=http://localhost:3000
# 선택: Windows의 codex.cmd 또는 Linux의 codex 실행 파일 절대 경로
CODEX_CLI_PATH=
```

`MONGODB_DB_NAME`을 생략하면 `dev-words`를 사용하고 `BETTER_AUTH_URL`을 생략하면 `http://localhost:3000`을 사용합니다. `BETTER_AUTH_SECRET`은 실제 서비스에서도 Better Auth 설정과 같은 값을 사용해야 합니다.

DB를 변경하지 않고 Seed 데이터 구성을 검사하려면 다음 명령을 사용합니다.

```bash
npm run seed -- --dry-run
```

실제로 MongoDB에 초기 데이터를 저장하려면 다음 명령을 사용합니다.

```bash
npm run seed
```

## 16. 데이터 연결과 인덱스

프로젝트 데이터에서 외래 키로 사용하는 `userId`와 `wordId`는 문자열로 저장합니다. Better Auth가 관리하는 컬렉션은 어댑터의 기본 ID 형식을 그대로 사용합니다.

MongoDB는 `wordId`가 실제 단어를 가리키는지 자동으로 보장하지 않습니다. 단어만 삭제하면 메모와 요청 내역의 `wordId`는 남을 수 있으므로, 화면에서 단어를 조회한 결과가 없을 때 `삭제된 단어` 상태로 안전하게 처리해야 합니다.

초기화 과정에서 다음 고유 인덱스를 준비합니다.

| 컬렉션 | 인덱스 | 목적 |
| --- | --- | --- |
| `words` | `slug` | 같은 상세 주소의 단어 중복 방지 |
| `memos` | `userId + wordId` | 사용자당 단어 하나의 메모만 허용 |
| `wordRequests` | `userId + normalizedWord`, `status: pending` | 같은 사용자의 처리 중인 동일 단어 요청 방지 |
| `wordEditRequests` | `userId + wordId`, `status: pending` | 같은 사용자의 처리 중인 동일 단어 수정 요청 방지 |
| `aiUsage` | `userId + type + dateKey` | 사용자별 일일 AI 기능 사용 횟수 집계 |
| `aiRuns` | `userId + type`, `status: running` | 같은 사용자의 같은 AI 기능 동시 실행 방지 |
| `quizSessions` | `expiresAt` TTL | 정답을 서버에만 보관하는 임시 퀴즈 세션 정리 |

처리 완료 또는 거절된 요청은 같은 조합으로 다시 생성할 수 있도록 요청 인덱스에는 `pending` 상태에만 적용되는 부분 고유 인덱스(Partial Unique Index)를 사용합니다.

## 17. AI 실행과 퀴즈

### 17.1 단어 요청과 승인

단어 요청은 하나로 통합합니다. 일반 사용자가 요청하면 `wordRequests`를 생성한 뒤 Codex CLI로 초안을 생성합니다. AI는 `name`, `meaning`, `slug`, `description`, `category`, `tags`, `codeExample`, `codeLanguage`만 만듭니다. 서버 검증을 통과한 초안은 요청의 `draft`에 저장하며 관리자가 승인해야 `words`에 공개합니다.

실패해도 요청은 보존하고 **자동생성 실패. 관리자 확인요망**을 표시합니다. 같은 정규화 이름의 대기 요청은 관리자가 묶어 처리합니다. 완료·등록불가 내역도 관리자 목록에 남으며 등록불가 사유는 필수입니다. 기존 `pending`, `completed`, `rejected` 값을 유지하고 화면에 **검증 대기중**, **처리완료**, **등록불가**로 표시합니다.

### 17.2 미니 퀴즈

홈 화면 상단의 퀴즈 안내 영역 또는 마이페이지에서 퀴즈를 시작합니다. 비로그인 이용자는 홈의 버튼으로 로그인 모달을 열고, 로그인 후 퀴즈로 이동할 수 있습니다. 관리자는 기존과 같이 퀴즈 대상이 아닙니다.

- 난이도: 하·중·상.
- 1회 출제: 무작위로 선택한 서로 다른 단어 5개에서 문제 5개.
- 모든 문제는 중복 없는 선택지 4개의 객관식.
- 풀이 화면 제목은 **AI 퀴즈**로 표시하며 선택한 난이도는 숨깁니다.
- 한 번에 한 문제를 표시합니다. 답을 선택하면 다음 문제로 이동하고 마지막 문제에서는 멈춥니다. 이전·다음 버튼으로 이동해 선택한 답을 확인하거나 수정할 수 있습니다.
- 답변은 문제 이동 중 유지되며 마지막 문제에서 5개 답변이 모두 있을 때만 정답 제출이 가능합니다.
- 하: 용어 뜻과 기본 언어·사용법. 중: 사용 상황과 코드 역할. 상: 개념 비교·선택 이유·실행 결과.
- 매번 무작위 추출하며 이전 회차에 나온 단어도 다시 나올 수 있습니다.
- 정답과 해설은 제출 전 브라우저에 전달하지 않습니다.
- 서버 채점으로 5점 만점 점수, 선택한 답, 정답, 해설을 공개합니다.
- **재도전**은 난이도 선택으로, **퀴즈 종료**는 마이페이지로 이동합니다.
- 한국 날짜 기준 하루 생성 5회(최초 1회와 재도전 4회). 생성 실패도 시작한 시도에 포함됩니다. 홈 퀴즈 배너에 로그인한 사용자의 오늘 도전 횟수와 남은 도전 횟수를 표시합니다. 횟수를 모두 사용하면 내일 다시 도전하도록 안내합니다.
- `quizSessions`에는 `userId`, `difficulty`, `questions`, `createdAt`, `expiresAt`을 저장합니다. 문제는 `wordId`, `question`, `choices`, `correctChoiceIndex`, `explanation`으로 구성합니다.
- 제출한 임시 세션은 즉시 삭제하며 미제출 세션은 1시간 만료 후 정리합니다. 결과 이력은 장기 저장하지 않습니다.

### 17.3 서버 실행과 제한

기존 호스트 Codex CLI 방식을 유지합니다. 서버의 `lib/ai`에서 `codex exec --ephemeral --sandbox read-only --skip-git-repo-check --output-schema <schema-file> -`를 실행합니다. 퀴즈 생성에는 빠른 `gpt-5.6-luna` 모델과 `low` 추론 강도를 사용합니다. 단어 초안 생성은 기존 CLI 기본 모델 설정을 유지합니다. 고정 프롬프트와 JSON Schema를 사용하고 사용자 입력은 stdin으로만 전달합니다.

프로젝트와 분리된 임시 폴더를 사용하고, DB 연결 문자열과 인증 비밀값은 자식 프로세스에 전달하지 않습니다. CLI 설치·인증이 필요하며 `CODEX_CLI_PATH`로 실행 경로를 지정할 수 있습니다. CLI 인증정보는 DB나 저장소에 복사하지 않습니다.

AI 단어 생성은 사용자별 하루 5회, 퀴즈도 별도로 하루 5회입니다. 같은 사용자의 같은 AI 기능은 한 번에 하나만 실행하며 요청 제한시간은 60초입니다. `aiUsage`는 `userId`, `type`, `dateKey`, `count`, `createdAt`, `updatedAt`을 사용합니다. `aiRuns`는 `userId`, `type`, `status`, `createdAt`, `expiresAt`으로 실행 잠금을 보관하며 완료 시 삭제하고 비정상 종료 시 2분 만료로 정리합니다.

### 17.4 기존 DB의 인덱스 갱신

`npm run seed -- --indexes-only`로 초기 사용자·단어·메모를 추가하지 않고 인덱스만 준비할 수 있습니다. `favorites`의 사용자·단어 고유 인덱스와 `recentWords`의 사용자 고유 인덱스를 포함합니다. 개발용 전체 초기 데이터 준비는 기존처럼 `npm run seed`를 사용합니다.


## 18. 검증

기본 검증은 `npm test`, `npm run lint`, `npm run build`입니다. DB 통합 테스트는 기본 실행에서 건너뛰며, 이름이 `dev-words-test-`로 시작하는 별도 DB를 지정해야 실행합니다.

```bash
MONGODB_DB_NAME=dev-words-test-local npm run seed -- --indexes-only
MONGODB_TEST_DB=dev-words-test-local node --test test/feature-data.test.js
```

통합 테스트는 자체 생성한 데이터만 정리합니다. 메모 이력과 재등록, 스크랩 중복 방지·해제, 최근 열람 순서·10개 제한·삭제, 요청 묶음 완료·등록불가, CLI 실패 요청 보존, AI 동시 실행·일일 제한, 퀴즈 세션 소유권·일회 제출, 단어 삭제를 확인합니다.

CLI 실행 시 `spawn codex ENOENT`가 발생하면 웹 서버의 PATH에서 Codex를 찾지 못한 것입니다. `.env.local`의 `CODEX_CLI_PATH`에 해당 호스트에서 확인한 실행 파일 절대 경로를 설정하고 서버를 재시작합니다. macOS에서도 이 설정을 사용할 수 있으며 호스트별 경로를 Git에 저장하지 않습니다.


## 19. 관리자 단어 등록·수정 이력

- 등록 경로 `source`: **관리자 작성**, **AI요청**. AI 초안으로 승인한 단어는 관리자가 내용을 수정해도 AI요청으로 유지합니다. 초안 없이 직접 작성한 단어는 관리자 작성입니다.
- Seed 단어의 `source`는 **초기 설정 데이터**입니다. 기존 Seed 단어의 출처만 갱신하려면 `npm run seed -- --sources-only`를 실행합니다. 출처가 없는 다른 과거 단어는 **초기 데이터**로 표시합니다.
- `words.history`: `{ type, userId, email, before, after, createdAt }`. 등록과 수정 당시 관리자와 내용을 기록합니다. `before`, `after`는 기존 단어 콘텐츠 필드 이름을 그대로 사용합니다.
- 수정 내용과 이력은 동일 문서에 한 번에 저장합니다. 다른 관리자가 동시에 수정한 경우 덮어쓰지 않고 재시도를 안내합니다.
- 삭제 전 `wordHistory`에 문자열 `wordId`, 등록 경로, 콘텐츠, 전체 이력, 등록·수정·삭제 시각을 보관합니다. 일반 단어 조회에서는 이력을 제외합니다.
- 관리자 페이지의 **등록된 단어 관리**에 등록 경로를 표시합니다. **단어 등록·수정 이력**에서 AI요청·관리자 작성·초기 데이터의 개수와 최근 등록 단어를 나란히 비교할 수 있습니다. 전체 목록은 등록 시각 최신순이며 Query String의 `source`로 출처를 필터링합니다. 초기 설정 데이터와 출처 없는 과거 단어는 모두 **초기 데이터** 필터에 포함됩니다. 단어를 펼치면 변경 전후 내용과 처리 관리자·시각, 삭제된 단어 이력을 확인합니다.
- 기능 적용 이전의 수정 내용과 관리자 정보는 복원할 수 없습니다.
