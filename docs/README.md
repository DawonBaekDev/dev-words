# 개발자 단어장 서비스 명세

## 1. 서비스 소개

이 서비스는 웹 개발을 공부하는 사람이 낯선 개발 용어를 검색하고, 쉬운 설명을 읽으며, 로그인 후 자신만의 메모와 AI 학습 기능을 사용할 수 있는 개발자 단어장입니다.

단어 이름, 직역 의미, 설명, 코드 예시는 공개 데이터입니다. 로그인하지 않은 이용자도 단어 목록, 검색 결과, 단어 상세 의미와 설명, 코드 예시를 볼 수 있습니다. 개인 메모, 새 단어 요청, 기존 단어 수정 요청은 로그인한 이용자만 사용할 수 있습니다.

서비스의 핵심 원칙은 다음과 같습니다.

- 단어장 데이터는 모든 이용자에게 공개합니다.
- 개인 메모는 작성한 이용자만 조회하고 수정할 수 있습니다.
- 일반 사용자는 단어를 직접 변경하지 않고 관리자에게 등록 또는 수정을 요청합니다.
- 관리자는 단어를 등록·수정·삭제하고 요청을 완료 또는 거절 처리합니다.
- 알림은 실시간으로 보내지 않고 마이페이지의 요청 상태 변화로 보여줍니다.

## 2. 이용자 역할과 접근 권한

서비스에서는 비로그인 이용자, 일반 사용자, 관리자를 구분합니다.

| 기능 | 비로그인 | 일반 사용자(`user`) | 관리자(`admin`) |
| --- | --- | --- | --- |
| 단어 목록·검색·상세 조회 | 가능 | 가능 | 가능 |
| 개인 메모 조회·작성·수정 | 불가능 | 본인 메모만 가능 | 제공하지 않음 |
| 관리자에게 새 단어 요청 | 로그인 모달 표시 | 가능 | 관리자 페이지에서 직접 등록 |
| AI 단어 요청 | 로그인 모달 표시 | 가능 | 가능 |
| AI 퀴즈 | 로그인 모달 표시 | 마이페이지에서 가능 | 관리자 페이지에서 가능 |
| 기존 단어 수정 요청 | 불가능 | 가능 | 단어를 직접 수정 |
| 마이페이지 | 불가능 | 가능 | 관리자 페이지로 대체 |
| 단어 등록·수정·삭제 | 불가능 | 불가능 | 가능 |
| 요청 완료·거절 처리 | 불가능 | 불가능 | 가능 |

화면 상단의 버튼도 현재 로그인 상태에 따라 달라집니다.

| 상태 | 표시할 버튼 |
| --- | --- |
| 비로그인 | 로그인 |
| 일반 사용자 | 마이페이지, 로그아웃 |
| 관리자 | 관리자 페이지, 로그아웃 |

관리자도 일반 사용자와 같은 단어 목록과 상세 설명을 봅니다. 단어 상세 화면에서는 개인 메모 버튼 대신 단어 **수정**과 **삭제** 버튼을 사용합니다.

권한 검사는 버튼을 숨기는 것만으로 끝내지 않습니다. 모든 저장·수정·삭제 Server Action에서 Better Auth 세션과 역할을 다시 확인합니다.

## 3. 화면과 URL 구성

| 화면 | 권장 URL | 역할 |
| --- | --- | --- |
| 단어 목록과 검색 | `/` | 전체 단어 조회, 검색, 카테고리 필터 |
| 단어 상세 | `/words/[slug]` | 설명 조회, 개인 메모 또는 관리자 단어 관리 |
| 마이페이지 | `/mypage` | 일반 사용자의 요청 내역 조회와 AI 퀴즈 시작 |
| AI 퀴즈 | `/quiz` | 난이도 선택, 3문제 풀이, 결과 확인 |
| 관리자 페이지 | `/admin` | 요청 목록 조회, 새 단어 등록, 관리자 AI 퀴즈 시작 |

로그인과 회원가입은 별도 페이지로 이동하지 않고 현재 화면 위에 표시하는 모달(Modal)로 구현합니다.

## 4. 단어 데이터

### 4.1 필드

| 필드 | 자료형 | 필수 | 설명 |
| --- | --- | --- | --- |
| `_id` | `ObjectId` | 자동 생성 | MongoDB가 만드는 단어 고유 ID |
| `name` | `String` | 필수 | 이용자에게 표시할 단어 이름 |
| `meaning` | `String` | 필수 | 영어 원어와 단어를 직역한 한국어 뜻 |
| `slug` | `String` | 필수 | 상세 주소와 중복 확인에 사용하는 고유한 값 |
| `description` | `String` | 필수 | 초보자가 이해할 수 있는 단어 설명 |
| `category` | `String` | 필수 | 단어의 대표 카테고리 하나 |
| `tags` | `String[]` | 선택 | 단어의 세부 특징을 나타내는 태그 목록 |
| `codeExample` | `String` | 필수 | 단어를 실제 코드에서 사용하는 짧은 예시 |
| `codeLanguage` | `String` | 필수 | 코드 예시의 언어를 나타내는 식별자 |
| `createdAt` | `Date` | 자동 생성 | 단어가 처음 등록된 시각 |
| `updatedAt` | `Date` | 자동 생성 | 단어가 마지막으로 수정된 시각 |

단어 하나는 다음과 같은 형태입니다.

```js
{
  name: "HTTP",
  meaning: "Hypertext Transfer Protocol : 하이퍼텍스트 전송 규약",
  slug: "http",
  description:
    "웹에서 브라우저와 서버가 요청과 응답을 주고받을 때 사용하는 통신 규칙입니다.",
  category: "웹 기초",
  tags: ["통신", "요청과 응답"],
  codeExample: `const response = await fetch("/api/words");
const words = await response.json();

console.log(words);`,
  codeLanguage: "javascript",
  createdAt: new Date(),
  updatedAt: new Date(),
}
```

### 4.2 직역 의미

`meaning`에는 기술 용어의 영어 원어와 직역한 한국어 뜻을 `영어 원어 : 한국어 뜻` 형식으로 저장합니다. 화면 이름이 한글인 단어도 영어 원어를 함께 기록합니다.

```js
{
  name: "브랜치",
  meaning: "branch : 나무의 가지",
}
```

약어는 가능한 경우 전체 영어 이름을 사용합니다.

```js
{
  name: "HTTP",
  meaning: "Hypertext Transfer Protocol : 하이퍼텍스트 전송 규약",
}
```

`meaning`은 Markdown 기호를 넣지 않은 일반 문자열로 저장하며, 현재 검색 대상에는 포함하지 않습니다.

### 4.3 카테고리와 태그

단어 하나에는 카테고리를 하나만 지정합니다. 처음 사용하는 카테고리는 다음 6개입니다.

1. 웹 기초
2. React
3. 데이터
4. Next.js
5. JavaScript
6. 기타

단어의 대표 분야를 알기 어렵다면 `기타`를 선택합니다. 태그는 선택 항목이며 여러 개를 지정할 수 있습니다. 태그가 없으면 빈 배열 `[]`로 저장합니다.

관리자 입력 화면에서는 태그를 쉼표로 구분해 작성합니다.

```text
통신, 요청과 응답, 웹
```

저장하기 전 앞뒤 공백을 제거하고 다음 배열로 변환합니다.

```js
["통신", "요청과 응답", "웹"]
```

### 4.4 슬러그

슬러그(Slug)는 단어 상세 주소의 마지막 부분입니다.

```text
/words/http
       └── HTTP 단어의 slug
```

슬러그는 영문 소문자, 숫자, 하이픈(`-`)만 사용하고 단어마다 고유해야 합니다. Seed 스크립트도 `slug`를 기준으로 이미 존재하는 단어인지 확인합니다.

### 4.5 코드 예시와 언어

모든 단어에는 설명과 함께 짧은 코드 예시를 저장합니다. `codeExample`에는 Markdown 코드 블록 기호 없이 코드 내용만 문자열로 저장하고, 화면에서 `<pre><code>` 요소로 표시합니다. 이렇게 하면 데이터와 화면 표현을 분리할 수 있습니다.

`codeLanguage`는 다음 네 값 중 하나만 사용합니다.

| 저장 값 | 화면 표시 | 사용 예 |
| --- | --- | --- |
| `javascript` | JavaScript | 일반 JavaScript, Node.js, MongoDB, Server Action |
| `jsx` | JSX | React 컴포넌트와 Next.js 화면 예시 |
| `bash` | Bash | Git과 터미널 명령 |
| `text` | Text | 폴더 구조처럼 실행 언어가 없는 예시 |

언어 이름을 제한하면 잘못된 철자나 서로 다른 표기(`js`, `JavaScript`, `javascript`)가 섞이는 것을 막고, 추후 syntax highlighting을 추가할 때 같은 값을 그대로 사용할 수 있습니다. 현재 검색 범위는 기존 규칙대로 `name`과 `description`이며 직역 의미와 코드 예시는 검색 대상에 포함하지 않습니다.

## 5. 검색

검색어가 단어의 `name` 또는 `description`에 포함되어 있으면 결과에 표시합니다.

- 부분 일치 검색을 사용합니다.
- 영문 대소문자를 구분하지 않습니다.
- 검색어의 앞뒤 공백은 제거합니다.
- 카테고리 필터와 검색어를 함께 사용할 수 있습니다.
- 검색과 카테고리는 Query String으로 관리합니다.

예를 들어 `요청`을 검색하면 설명에 해당 표현이 들어 있는 HTTP가 결과에 포함될 수 있습니다.

```text
/?query=요청&category=웹%20기초
```

검색 결과가 없으면 기존 관리자 요청 기능과 AI 생성 기능을 구분해 두 개의 버튼을 표시합니다.

```text
“웹소켓”에 대한 검색 결과가 없습니다.

[AI 단어 요청하기] [관리자에게 단어 요청하기]
```

비로그인 이용자가 두 버튼 중 하나를 누르면 로그인 모달을 표시합니다. 로그인 또는 회원가입 후에도 현재 검색어와 화면을 유지합니다.

로그인한 이용자가 **관리자에게 단어 요청하기**를 누르면 현재 검색어를 요청할 단어로 보여주는 입력 영역을 엽니다. **저장**을 누른 뒤 “이 단어를 요청하시겠습니까?” 확인창에서 **확인**을 눌러야 실제 요청을 생성합니다. 입력 영역에서 취소하면 요청을 만들지 않고 영역을 닫습니다.

**AI 단어 요청하기**는 관리자 요청을 만들지 않고 Codex CLI로 단어 정보를 생성하는 별도 기능입니다. 자세한 동작은 17장의 AI 기능 명세를 따릅니다.

## 6. 로그인과 회원가입

로그인과 회원가입은 Better Auth의 이메일·비밀번호 인증을 사용합니다.

### 6.1 로그인 모달

로그인 모달에는 다음 요소를 표시합니다.

- 이메일 입력
- 비밀번호 입력
- 로그인 버튼
- 회원가입 화면으로 전환하는 버튼
- 모달 닫기 버튼

이메일이 없거나 비밀번호가 틀린 경우를 구분하지 않고 다음 메시지 하나를 사용합니다.

```text
이메일 또는 비밀번호를 확인해 주세요.
```

로그인에 성공하면 모달을 닫고 현재 페이지를 새로고침하여 로그인 상태에 맞는 기능을 표시합니다.

### 6.2 회원가입

회원가입 화면에는 이용자가 입력하는 이메일과 비밀번호만 표시합니다. Better Auth가 내부적으로 요구하는 사용자 이름은 서버에서 이메일을 바탕으로 만들어 전달합니다.

- 이메일은 올바른 이메일 형식이어야 합니다.
- 비밀번호는 최소 4자입니다.
- 영문·숫자·특수문자의 조합은 강제하지 않습니다.
- 이미 가입된 이메일은 다시 사용할 수 없습니다.

회원가입 성공 시 자동 로그인한 뒤 현재 주소를 유지한 채 새로고침합니다. 단어 상세 화면에서 가입했다면 같은 단어 상세 화면에 남아 바로 메모 기능을 사용할 수 있습니다.

### 6.3 로그아웃

로그아웃하면 Better Auth 세션을 종료한 뒤 현재 주소를 유지한 채 새로고침합니다. 개인 메모 데이터는 삭제하지 않으며, 다시 로그인하면 확인할 수 있습니다.

## 7. 개인 메모

개인 메모는 로그인한 일반 사용자만 사용할 수 있습니다. 같은 단어라도 사용자마다 서로 다른 메모를 가집니다. 다른 사용자의 메모는 조회하거나 수정할 수 없습니다.

### 7.1 데이터 구조

| 필드 | 자료형 | 설명 |
| --- | --- | --- |
| `_id` | `ObjectId` | 메모 고유 ID |
| `userId` | `String` | Better Auth 사용자 ID |
| `wordId` | `String` | 메모가 속한 단어 ID |
| `content` | `String` | 사용자가 작성한 개인 메모 |
| `createdAt` | `Date` | 최초 작성 시각 |
| `updatedAt` | `Date` | 마지막 수정 시각 |

한 사용자는 같은 단어에 메모를 하나만 작성할 수 있습니다. 따라서 `userId + wordId` 조합은 고유해야 합니다.

### 7.2 화면 동작

해당 단어에 메모가 없을 때 별도의 안내 문구는 표시하지 않고 **메모하기** 버튼만 보여줍니다.

1. 메모하기를 누르면 단어 상세 화면의 버튼 아래에 입력 영역이 펼쳐집니다.
2. 저장을 누르면 “메모를 저장하시겠습니까?” 확인창을 표시합니다.
3. 확인창에서 취소하면 입력 내용을 유지합니다.
4. 확인을 누르면 실제 저장을 실행합니다.
5. 성공하면 “메모가 저장되었습니다.”를 표시하고 입력창을 닫습니다.
6. 저장된 메모, 작성 시각, 수정 시각, 수정 버튼을 같은 위치에 표시합니다.

기존 메모를 수정할 때는 기존 내용을 입력창에 채웁니다. 수정 성공 시 “메모가 수정되었습니다.”를 표시합니다. 입력 영역의 취소 버튼은 변경 내용을 버리고 원래 메모 보기로 돌아갑니다.

메모가 비어 있거나 공백만 있으면 다음 오류를 표시합니다.

```text
메모 내용을 입력해 주세요.
```

## 8. 새 단어 요청

검색 결과가 없을 때 로그인한 사용자는 관리자에게 새 단어 등록을 요청할 수 있습니다.

### 8.1 데이터 구조

| 필드 | 자료형 | 설명 |
| --- | --- | --- |
| `_id` | `ObjectId` | 요청 고유 ID |
| `userId` | `String` | 요청한 사용자 ID |
| `requestedWord` | `String` | 사용자가 요청한 현재 단어 이름 |
| `normalizedWord` | `String` | 중복 검사와 묶음 처리에 사용하는 정규화된 이름 |
| `status` | `String` | `pending`, `completed`, `rejected` 중 하나 |
| `wordId` | `String` 또는 없음 | 관리자가 등록한 단어 ID |
| `rejectionReason` | `String` 또는 없음 | 관리자가 작성한 거절 사유 |
| `createdAt` | `Date` | 최초 요청 시각 |
| `updatedAt` | `Date` | 요청 수정 또는 처리 시각 |

`normalizedWord`는 요청 단어의 앞뒤 공백을 제거하고 영문을 소문자로 바꾼 값입니다. 같은 사용자가 동일한 `normalizedWord`에 대해 가질 수 있는 `pending` 요청은 하나뿐입니다.

| 기존 상태 | 같은 단어 재요청 |
| --- | --- |
| `pending` | 불가능 |
| `completed` | 검색 결과에 단어가 나타나므로 요청 버튼 미표시 |
| `rejected` | 가능 |

거절 후 재요청하면 이전 데이터를 되돌리지 않고 새 요청을 만듭니다. 과거 거절 기록은 마이페이지에 그대로 남습니다.

### 8.2 사용자의 요청 수정

사용자는 `pending` 상태인 요청 단어의 오타를 수정할 수 있습니다. 요청 자체를 취소하거나 삭제할 수는 없습니다.

- 요청 수정 시 `requestedWord`와 `normalizedWord`를 함께 변경합니다.
- `createdAt`은 유지하고 `updatedAt`만 변경합니다.
- 이전 오타 내용은 별도로 보관하지 않습니다.
- 이미 같은 사용자의 동일한 `pending` 요청이 있으면 수정을 거절합니다.
- `completed` 또는 `rejected` 요청은 수정할 수 없습니다.

## 9. 기존 단어 수정 요청

로그인한 일반 사용자의 단어 상세 화면에는 **메모하기** 옆에 **수정 요청하기** 버튼을 표시합니다.

### 9.1 데이터 구조

| 필드 | 자료형 | 설명 |
| --- | --- | --- |
| `_id` | `ObjectId` | 수정 요청 고유 ID |
| `userId` | `String` | 요청한 사용자 ID |
| `wordId` | `String` | 수정 대상 단어 ID |
| `message` | `String` | 사용자가 작성한 자유 형식의 수정 의견 |
| `status` | `String` | `pending`, `completed`, `rejected` 중 하나 |
| `rejectionReason` | `String` 또는 없음 | 관리자가 작성한 거절 사유 |
| `createdAt` | `Date` | 최초 요청 시각 |
| `updatedAt` | `Date` | 요청 수정 또는 처리 시각 |

같은 사용자는 같은 단어에 `pending` 수정 요청을 하나만 가질 수 있습니다. 완료되거나 거절된 뒤에는 새 수정 요청을 보낼 수 있습니다.

### 9.2 작성 화면

수정 요청은 자유롭게 작성할 수 있는 `message` 입력창 하나만 사용합니다. `textarea`에는 다음 예시를 `placeholder`로 표시합니다.

```text
예시)
수정할 부분: 단어 설명
수정 이유: 현재 설명이 초보자가 이해하기 어렵습니다.
수정 제안: HTTP는 브라우저와 서버가 데이터를 주고받기 위한 약속입니다.
```

Placeholder는 안내일 뿐 DB에 저장되지 않습니다. 사용자가 실제로 입력한 내용만 `message`로 저장합니다. 빈 내용이나 공백만 입력하면 “수정 요청 내용을 입력해 주세요.”를 표시합니다.

사용자는 `pending` 요청의 `message`를 수정할 수 있지만 요청을 취소하거나 삭제할 수 없습니다. 수정 시 이전 내용은 보관하지 않고 현재 내용으로 덮어쓰며 `updatedAt`을 변경합니다.

## 10. 마이페이지

마이페이지는 일반 사용자가 본인의 요청 내역을 확인하고 AI 퀴즈를 시작하는 화면입니다. 실시간 알림, 읽음·안 읽음 상태, 별도의 알림 컬렉션은 현재 구현 범위에 포함하지 않습니다.

화면 상단에 **AI 퀴즈** 버튼을 표시하며, 버튼을 누르면 난이도를 선택하고 퀴즈를 시작할 수 있는 `/quiz`로 이동합니다.

요청 종류별로 두 개의 아코디언을 표시합니다.

```text
▼ 새 단어 요청 내역 2건
▶ 수정 요청 내역 3건
```

각 아코디언 안에서는 요청을 상태별로 다시 나누지 않고 최근 요청부터 하나의 목록으로 보여줍니다.

| 상태 | 화면 표시 |
| --- | --- |
| `pending` | 요청 내용, 요청일, 마지막 수정일, 요청 수정 버튼 |
| `completed` | 요청 내용, 요청일, 완료일, 대상 단어가 있으면 단어 보러 가기 버튼 |
| `rejected` | 요청 내용, 요청일, 거절 사유, 거절 처리일, 대상 단어가 있으면 단어 보러 가기 버튼 |

새 단어 요청이나 기존 단어 수정 요청의 `wordId`에 해당하는 단어가 현재 존재할 때만 **단어 보러 가기** 버튼을 표시합니다. 거절되어 단어가 생성되지 않았거나 관리자가 해당 단어를 삭제했다면 `삭제된 단어`라고 표시하고 상세 화면 이동 버튼은 숨깁니다. 요청 내용과 처리 상태는 과거 내역으로 계속 보여줍니다.

## 11. 관리자 페이지

관리자 페이지에는 **새 단어 요청 목록**, **기존 단어 수정 요청 목록**, **새 단어 등록**, **AI 퀴즈** 진입 버튼을 같은 화면에 표시합니다. 관리자는 마이페이지를 사용하지 않으므로 AI 퀴즈 버튼을 관리자 페이지에서 제공합니다.

두 요청 목록은 독립적으로 열고 닫을 수 있는 아코디언입니다.

```text
▼ 새 단어 요청 3건
▶ 기존 단어 수정 요청 2건

[새 단어 등록]
```

### 11.1 새 단어 요청 처리

같은 `normalizedWord`의 `pending` 요청은 관리자 목록에서 묶어서 보여줍니다.

```text
웹소켓 · 요청 인원 3명

[단어 등록하기] [요청 거절하기]
```

단어 등록하기를 누르면 새 단어 등록 입력 영역이 열리고 요청 단어가 이름 입력칸에 자동으로 들어갑니다. 관리자는 직역 의미, 설명, 카테고리, 태그, 슬러그, 코드 예시, 코드 언어를 입력합니다.

- 저장 후 확인을 눌러야 실제 등록을 실행합니다.
- 입력 영역에서 취소하면 입력 내용을 버리고 영역을 닫습니다.
- 등록 성공 시 같은 단어의 모든 `pending` 요청을 `completed`로 변경합니다.
- 각 요청에 생성된 단어의 `wordId`를 저장합니다.
- 각 요청의 `updatedAt`을 등록 완료 시각으로 변경합니다.
- 처리 후 관리자 페이지로 돌아와 목록을 다시 조회합니다.

요청 거절하기를 누르면 요청 아래에 거절 사유 `textarea`를 표시합니다. 거절 사유는 필수이며 저장·확인 후 같은 단어의 모든 `pending` 요청을 같은 사유로 `rejected` 처리합니다.

```text
예시)
요청하신 단어가 이미 다른 이름으로 등록되어 있습니다.
기존 단어를 확인해 주세요.
```

### 11.2 수정 요청 처리

수정 요청은 같은 단어에 여러 건이 있어도 하나로 합치지 않습니다. 내용이 서로 다를 수 있기 때문에 관리자가 선택한 요청을 각각 처리합니다.

관리자가 **단어 수정하기**를 누르면 해당 단어 상세 화면으로 이동하고 기존 정보가 입력 영역으로 바뀝니다. 저장 성공 시 선택한 수정 요청 하나만 `completed`로 변경합니다. 같은 단어의 나머지 요청은 `pending`을 유지합니다.

관리자가 요청 목록을 거치지 않고 상세 화면에서 직접 수정한 경우에는 단어만 변경하며 어떤 수정 요청도 완료 처리하지 않습니다.

요청 거절하기를 누르면 해당 요청 아래에 거절 사유 입력 영역을 표시합니다. 사유를 저장하고 확인하면 선택한 요청 하나만 `rejected`로 변경합니다.

## 12. 관리자 단어 등록·수정·삭제

### 12.1 등록과 수정

새 단어 등록 입력 항목은 다음과 같습니다.

- 단어 이름
- 단어 직역 의미
- 단어 설명
- 카테고리
- 태그
- 슬러그
- 코드 예시
- 코드 언어

관리자 단어 상세 화면에서 **수정**을 누르면 표시 중인 정보가 기존 값이 채워진 입력 영역으로 바뀝니다. 취소하면 변경 내용을 버리고 원래 상세 화면으로 돌아갑니다.

요청을 통해 들어온 수정에 성공하면 관리자 페이지의 수정 요청 목록으로 돌아갑니다. 단어 상세 화면에서 직접 수정한 경우에는 현재 상세 화면에 머뭅니다.

### 12.2 단어만 하드 삭제

삭제는 `words` 컬렉션에서 선택한 단어 문서 하나만 제거하는 하드 삭제(Hard Delete)로 처리합니다. 단어 삭제 한 번 때문에 여러 컬렉션에 연쇄 삭제 쿼리를 실행하지 않습니다.

단어와 연결된 다음 데이터는 삭제하거나 수정하지 않고 기존 상태 그대로 보관합니다.

- 사용자가 작성한 개인 메모
- 해당 단어에 대한 기존 수정 요청
- 해당 단어의 `wordId`가 연결된 새 단어 요청 내역
- 사용자 계정과 다른 단어 데이터

삭제된 단어의 상세 주소로 접근하면 찾을 수 없음 화면을 표시합니다. 마이페이지와 관리자 페이지에서는 남아 있는 요청 내역을 계속 보여주되, 대상 단어를 찾을 수 없으면 `삭제된 단어`라고 표시하고 **단어 보러 가기** 또는 **단어 수정하기**처럼 단어가 필요한 버튼은 숨깁니다.

단어 자체는 복구할 수 없으므로 다음 확인창을 표시합니다.

```text
이 단어만 삭제되며 복구할 수 없습니다.
연결된 개인 메모와 요청 내역은 기록으로 남습니다.

삭제하시겠습니까?
```

삭제 Server Action에서는 관리자 세션과 역할, 단어 ID, 단어 존재 여부를 다시 확인한 뒤 `words` 컬렉션에 한 번의 삭제 작업을 실행합니다. 한 문서만 삭제하므로 여러 컬렉션을 묶는 MongoDB 트랜잭션은 사용하지 않습니다. 삭제된 단어 문서는 남지 않으므로 `isDeleted`, `deletedAt`, 삭제 시점의 `updatedAt`도 저장하지 않습니다.

## 13. 저장·확인·취소와 결과 메시지

작성과 수정 기능은 공통으로 다음 순서를 따릅니다.

1. 사용자가 내용을 입력합니다.
2. **저장**을 누릅니다.
3. 확인창에서 **확인** 또는 **취소**를 선택합니다.
4. 확인을 누르면 서버 처리를 실행합니다.
5. 취소를 누르면 입력 내용을 유지한 채 작성·수정 화면으로 돌아갑니다.
6. 서버 처리 결과에 따라 성공 또는 오류 메시지를 표시합니다.

입력 영역 자체의 취소 버튼은 내용을 저장하지 않고 입력 영역을 닫습니다. 요청 내역의 **요청 수정** 화면에서 취소를 눌러도 요청 자체가 취소되는 것은 아닙니다.

처리 결과는 화면 상태에서 다음처럼 구분합니다.

```js
{
  type: "success",
  message: "메모가 저장되었습니다.",
}
```

```js
{
  type: "error",
  message: "메모를 저장하지 못했습니다. 잠시 후 다시 시도해 주세요.",
}
```

수정 요청 데이터의 `message`는 사용자가 작성한 의견을 DB에 저장하는 필드입니다. 위 예시의 결과 `message`는 저장 처리의 성공 또는 실패를 잠시 화면에 알려주는 UI 상태입니다. 이름은 같지만 쓰임과 저장 위치가 다릅니다.

| 상황 | 메시지 |
| --- | --- |
| 새 메모 저장 성공 | 메모가 저장되었습니다. |
| 기존 메모 수정 성공 | 메모가 수정되었습니다. |
| 새 단어 요청 성공 | 단어 요청이 등록되었습니다. |
| 수정 요청 성공 | 수정 요청이 등록되었습니다. |
| 요청 내용 수정 성공 | 요청 내용이 수정되었습니다. |
| 관리자 단어 등록 성공 | 단어가 등록되었습니다. |
| 관리자 단어 수정 성공 | 단어가 수정되었습니다. |
| 관리자 단어 삭제 성공 | 단어가 삭제되었습니다. |
| 요청을 통한 단어 수정 성공 | 단어 수정과 요청 처리가 완료되었습니다. |
| 요청 거절 성공 | 요청이 거절되었습니다. |
| 관리자 권한 없음 | 관리자만 이용할 수 있는 기능입니다. |

## 14. 날짜와 시간 규칙

등록·수정·요청·요청 처리 데이터에는 `createdAt`과 `updatedAt`을 사용합니다.

- 새 데이터 생성 시 두 값은 같은 시각입니다.
- 실제 DB 데이터가 변경되었을 때만 `updatedAt`을 변경합니다.
- 입력창 열기, 취소, 검증 실패, 서버 처리 실패는 `updatedAt`을 변경하지 않습니다.
- 하드 삭제된 단어 문서는 남지 않으므로 삭제 시각을 기록하지 않습니다.
- 단어 삭제 시 관련 메모와 요청 내역은 수정하지 않으므로 해당 데이터의 `updatedAt`도 변경하지 않습니다.

화면에서는 상태에 따라 `updatedAt`을 마지막 수정일, 등록 완료일, 수정 완료일 또는 거절 처리일로 표현합니다.

## 15. 초기 데이터(Seed Data)

`scripts/seeds.js`는 개발 환경에 다음 데이터를 준비합니다.

| 데이터 | 개수 | 중복 확인 기준 |
| --- | ---: | --- |
| 단어 | 30개 | `slug` |
| 테스트 사용자 | 3명 | `email` |
| 개인 메모 | 3개 | `userId + wordId` |

새 단어 요청과 수정 요청은 초기 데이터에 넣지 않습니다. 실제 기능을 사용하며 생성합니다.

Seed는 다음 순서로 실행합니다.

1. Better Auth로 테스트 사용자를 생성하고 사용자 ID를 확인합니다.
2. 카테고리별 단어, 직역 의미, 코드 예시를 저장하고 단어 ID를 확인합니다.
3. 사용자 ID와 단어 ID를 연결해 개인 메모를 저장합니다.

30개 초기 단어에는 모두 `meaning`, `codeExample`, `codeLanguage`가 들어 있습니다. 기존 단어에서 `meaning`이나 코드 필드가 없거나 값이 올바르지 않을 때만 해당 필드를 Seed 값으로 보충하고 `updatedAt`을 보충 시각으로 변경합니다. 이미 유효한 직역 의미와 코드 예시를 비롯해 이름, 설명, 카테고리, 태그 등 사용자가 수정한 값은 덮어쓰지 않습니다.

스크립트를 다시 실행해도 없는 사용자, 단어, 메모만 추가하며 유효한 기존 데이터는 유지합니다. 따라서 사용자가 변경한 비밀번호, 개인 메모, 직역 의미, 코드 예시를 Seed 데이터로 되돌리지 않습니다.

### 15.1 테스트 계정

아래 계정은 개발 환경에서만 사용합니다.

| 이메일 | 비밀번호 | 역할 | 초기 메모 |
| --- | --- | --- | --- |
| `learner1@example.com` | `DevStudy1!Pass` | `admin` | HTTP |
| `learner2@example.com` | `DevStudy2!Pass` | `user` | useState |
| `learner3@example.com` | `DevStudy3!Pass` | `user` | 배열 |

첫 번째 사용자는 관리자이며, 나머지 두 사용자는 일반 사용자입니다. 비밀번호는 Better Auth API를 통해 해시된 후 `account` 컬렉션에 저장합니다. 원문 비밀번호를 직접 DB에 저장하지 않습니다.

관리자 계정의 HTTP 메모도 사용자·단어 연결을 검증하기 위한 초기 데이터로 저장됩니다. 현재 화면 명세에서는 관리자에게 개인 메모 UI를 표시하지 않으므로 이 메모는 관리자 화면에 노출되지 않습니다.

### 15.2 실행 환경

루트의 `.env.local`에 다음 환경 변수가 필요합니다.

```dotenv
MONGODB_URI=mongodb://127.0.0.1:27017
MONGODB_DB_NAME=dev-words
BETTER_AUTH_SECRET=32자 이상의 충분히 긴 임의 문자열
BETTER_AUTH_URL=http://localhost:3000
# 선택: Windows의 codex.cmd 또는 Linux의 codex 실행 파일 절대 경로
CODEX_CLI_PATH=
```

`MONGODB_DB_NAME`을 생략하면 `dev-words`를 사용하고 `BETTER_AUTH_URL`을 생략하면 `http://localhost:3000`을 사용합니다. `BETTER_AUTH_SECRET`은 실제 서비스에서도 Better Auth 설정과 같은 값을 사용해야 합니다.

DB를 변경하지 않고 Seed 데이터 구성을 검사하려면 다음 명령을 사용합니다.

```bash
npm run seed -- --dry-run
```

실제로 MongoDB에 초기 데이터를 저장하려면 다음 명령을 사용합니다.

```bash
npm run seed
```

## 16. 데이터 연결과 인덱스

프로젝트 데이터에서 외래 키로 사용하는 `userId`와 `wordId`는 문자열로 저장합니다. Better Auth가 관리하는 컬렉션은 어댑터의 기본 ID 형식을 그대로 사용합니다.

MongoDB는 `wordId`가 실제 단어를 가리키는지 자동으로 보장하지 않습니다. 단어만 삭제하면 메모와 요청 내역의 `wordId`는 남을 수 있으므로, 화면에서 단어를 조회한 결과가 없을 때 `삭제된 단어` 상태로 안전하게 처리해야 합니다.

초기화 과정에서 다음 고유 인덱스를 준비합니다.

| 컬렉션 | 인덱스 | 목적 |
| --- | --- | --- |
| `words` | `slug` | 같은 상세 주소의 단어 중복 방지 |
| `memos` | `userId + wordId` | 사용자당 단어 하나의 메모만 허용 |
| `wordRequests` | `userId + normalizedWord`, `status: pending` | 같은 사용자의 처리 중인 동일 단어 요청 방지 |
| `wordEditRequests` | `userId + wordId`, `status: pending` | 같은 사용자의 처리 중인 동일 단어 수정 요청 방지 |
| `aiUsage` | `userId + type + dateKey` | 사용자별 일일 AI 기능 사용 횟수 집계 |
| `aiRuns` | `userId + type`, `status: running` | 같은 사용자의 같은 AI 기능 동시 실행 방지 |
| `quizSessions` | `expiresAt` TTL | 정답을 서버에만 보관하는 임시 퀴즈 세션 정리 |

처리 완료 또는 거절된 요청은 같은 조합으로 다시 생성할 수 있도록 요청 인덱스에는 `pending` 상태에만 적용되는 부분 고유 인덱스(Partial Unique Index)를 사용합니다.

## 17. AI 기능과 Codex CLI 연동

AI 기능은 웹 개발을 공부하는 사용자가 등록되지 않은 용어의 쉬운 설명을 생성하고, 등록된 단어를 바탕으로 퀴즈를 풀 수 있게 합니다. AI 실행에는 프로젝트 패키지로 설치한 라이브러리가 아니라 호스트 운영체제에 설치된 Codex CLI를 사용합니다.

AI 기능은 별도 npm 패키지나 브라우저 직접 실행 없이, 서버 전용 Server Action과 호스트 OS의 Codex CLI로 구현합니다.

### 17.1 AI 기능 이용 권한

AI 기능은 Better Auth 세션이 있는 로그인 사용자만 이용할 수 있습니다.

| 기능 | 비로그인 | 일반 사용자(`user`) | 관리자(`admin`) |
| --- | --- | --- | --- |
| 일반 단어 검색 | 가능 | 가능 | 가능 |
| AI 단어 요청 | 로그인 모달 표시 | 가능 | 가능 |
| AI 퀴즈 | 로그인 모달 표시 | 마이페이지에서 가능 | 관리자 페이지에서 가능 |

비로그인 사용자가 검색 결과의 **AI 단어 요청하기** 버튼을 누르면 로그인 모달을 표시합니다. 로그인 또는 회원가입이 끝나면 원래 검색어가 있는 주소로 돌아와 다시 요청할 수 있게 합니다.

버튼 노출 여부만으로 권한을 판단하지 않습니다. AI 단어 요청과 AI 퀴즈를 실행하는 모든 Server Action에서 Better Auth 세션을 다시 확인합니다.

### 17.2 AI 단어 요청

검색한 개발 용어가 등록된 단어장에 없을 때 로그인 사용자는 **AI 단어 요청하기**를 사용할 수 있습니다.

#### 동작 순서

1. 사용자가 개발 용어를 검색합니다.
2. 서버가 단어 이름과 설명에서 기존 검색 결과를 확인합니다.
3. 검색 결과가 없으면 **AI 단어 요청하기** 버튼을 표시합니다.
4. 사용자가 버튼을 누르면 Server Action이 로그인 세션과 검색어를 검증합니다.
5. AI 실행 직전에 같은 이름 또는 slug의 단어가 생성되었는지 DB에서 다시 확인합니다.
6. 기존 단어가 없으면 호스트 OS의 Codex CLI에 단어 정보 생성을 요청합니다.
7. 서버가 Codex의 JSON 결과를 프로젝트의 단어 규칙으로 다시 검증합니다.
8. 검증을 통과하면 중복 여부를 한 번 더 확인한 뒤 `words` 컬렉션에 저장합니다.
9. 저장된 단어의 `/words/[slug]` 상세 화면으로 이동합니다.

요청 처리 중에는 버튼을 비활성화하고 **AI가 단어 설명을 만들고 있습니다.**라는 로딩 문구를 표시합니다. Codex 실행 실패, 시간 초과, 로그인 만료, JSON 형식 오류 또는 DB 저장 실패가 발생하면 단어를 저장하지 않고 다시 시도할 수 있는 오류 메시지를 표시합니다.

기존의 **관리자에게 단어 요청하기** 기능은 함께 유지합니다. 사용자는 즉시 AI 설명을 생성하거나 관리자 검토를 기다리는 방식 중 하나를 선택할 수 있습니다.

#### AI 단어 출력 구조

Codex에는 다음 필드만 생성하도록 JSON Schema를 제공합니다.

```js
{
  name: "WebSocket",
  meaning: "web socket : 웹의 통신 연결 지점",
  slug: "websocket",
  description:
    "브라우저와 서버가 연결을 유지하면서 양쪽에서 실시간으로 데이터를 주고받을 수 있게 하는 통신 방식입니다.",
  category: "웹 기초",
  tags: ["통신", "실시간"],
  codeExample: `const socket = new WebSocket("wss://example.com/socket");

socket.addEventListener("message", (event) => {
  console.log(event.data);
});`,
  codeLanguage: "javascript",
}
```

각 필드는 다음 조건을 만족해야 합니다.

- `name`: 사용자가 요청한 개발 용어와 같은 의미여야 합니다.
- `meaning`: `영어 원어 : 한국어 뜻` 형식의 비어 있지 않은 문자열이어야 합니다.
- `slug`: 영문 소문자, 숫자, 하이픈만 사용해야 합니다.
- `description`: 초급 학습자가 이해할 수 있는 한국어 설명이어야 합니다.
- `category`: `웹 기초`, `React`, `데이터`, `Next.js`, `JavaScript`, `기타` 중 하나여야 합니다.
- `tags`: 문자열 배열이며 태그가 없으면 `[]`를 사용합니다.
- `codeExample`: 용어를 이해하는 데 도움이 되는 짧고 비어 있지 않은 코드여야 합니다.
- `codeLanguage`: `javascript`, `jsx`, `bash`, `text` 중 하나여야 합니다.
- 정의하지 않은 추가 필드는 허용하지 않습니다.

MongoDB의 `_id`, `createdAt`, `updatedAt`은 AI가 만들지 않습니다. 서버가 검증을 통과한 데이터에 현재 시각을 추가하고 MongoDB가 `_id`를 생성하게 합니다.

AI가 만든 단어도 일반 단어와 같은 목록, 검색, 상세 화면에서 조회합니다. 관리자는 기존 관리자 기능으로 직역 의미, 설명, 카테고리, 태그, slug, 코드 예시, 코드 언어를 수정하거나 단어를 삭제할 수 있습니다.

### 17.3 AI 퀴즈

로그인한 일반 사용자는 마이페이지의 **AI 퀴즈** 버튼을 통해 퀴즈를 시작합니다. 관리자는 관리자 페이지의 같은 버튼을 사용합니다.

#### 동작 순서

1. 로그인 사용자가 AI 퀴즈 화면으로 이동합니다.
2. `초급`, `중급`, `고급` 중 하나의 난이도를 선택합니다.
3. Server Action이 로그인 세션과 난이도를 검증합니다.
4. 서버가 현재 `words` 컬렉션에서 퀴즈에 사용할 단어를 선택합니다.
5. 선택한 단어의 이름, 직역 의미, 설명, 카테고리, 태그, 코드 예시, 코드 언어만 Codex CLI에 전달합니다.
6. Codex가 선택한 난이도에 맞는 객관식 문제 3개를 JSON으로 생성합니다.
7. 서버가 문제 수, 선택지, 정답 위치, 단어 연결을 검증합니다.
8. 브라우저에는 문제와 선택지만 전달하고 정답과 해설은 노출하지 않습니다.
9. 사용자가 세 문제의 답을 모두 선택한 뒤 **정답 제출**을 누릅니다.
10. 서버가 직접 채점한 뒤 점수, 정답, 해설을 결과 화면에 표시합니다.

한 문제를 1점으로 계산하고 총점은 `0점`부터 `3점`까지 표시합니다. AI에게 사용자의 정답을 다시 보내 채점하지 않고, 처음 생성할 때 받은 정답 번호로 서버가 채점합니다.

#### 난이도 기준

| 난이도 | 출제 기준 |
| --- | --- |
| 초급 | 용어 이름과 기본 설명을 연결하는 문제 |
| 중급 | 실제 사용 상황이나 코드 역할을 이해하는 문제 |
| 고급 | 비슷한 개념 비교, 선택 이유, 동작 결과를 판단하는 문제 |

#### AI 퀴즈 출력 구조

퀴즈는 정확히 4개의 중복 없는 선택지를 가진 3문제로 생성합니다. 정답과 해설은 브라우저에 보내지 않고 임시 퀴즈 세션에만 보관합니다.

```js
{
  difficulty: "초급",
  questions: [
    {
      wordId: "MongoDB 단어 ID 문자열",
      question: "HTTP의 역할로 가장 알맞은 것은 무엇인가요?",
      choices: [
        "브라우저와 서버가 요청과 응답을 주고받는 규칙",
        "데이터를 배열로 저장하는 JavaScript 문법",
        "React 컴포넌트의 상태를 만드는 함수",
        "Git에서 작업 흐름을 나누는 기능",
      ],
      correctChoiceIndex: 0,
      explanation:
        "HTTP는 웹에서 브라우저와 서버가 요청과 응답을 주고받을 때 사용하는 통신 규칙입니다.",
    },
  ],
}
```

Codex 출력에는 정확히 3개의 문제가 있어야 하며 각 `wordId`는 실제 DB 단어를 가리켜야 합니다. 선택지는 같은 문제 안에서 중복될 수 없고 `correctChoiceIndex`는 선택지 배열 범위 안에 있어야 합니다.

### 17.4 호스트 OS의 Codex CLI 사용 방식

프로젝트는 Codex CLI를 npm 의존성으로 설치하지 않습니다. Next.js 서버 프로세스가 실행 중인 호스트 운영체제의 PATH에서 `codex` 명령을 찾아 사용합니다.

현재 개발 환경은 다음과 같습니다.

| 항목 | 현재 값 |
| --- | --- |
| 운영체제 | Windows 11 |
| Codex CLI | 호스트 OS에 설치됨 |
| 확인된 버전 | `codex-cli 0.154.0-alpha.6.2` (Windows 실제 실행 파일) |
| 인증 상태 | ChatGPT 계정으로 로그인됨 |

버전 번호는 2026년 9월 16일 확인 당시의 값이며, 서비스 로직이 특정 패치 버전에 의존하지 않게 구현합니다. 다음 명령으로 호스트 상태를 확인할 수 있습니다.

```powershell
codex --version
codex login status
```

향후 Linux 배포 환경에서도 다음 조건을 준비합니다.

1. Linux 호스트 또는 컨테이너 이미지에 Codex CLI를 설치합니다.
2. 웹 서버 전용 Linux 사용자 계정을 만들고 해당 계정으로 Codex CLI 로그인을 완료합니다.
3. 같은 사용자 계정에서 `codex --version`과 `codex login status`가 성공하는지 확인합니다.
4. Next.js 서버 프로세스의 PATH에서 `codex` 명령을 찾을 수 있게 합니다.
5. 애플리케이션을 시작할 때 CLI 존재 여부와 로그인 상태를 점검합니다.

애플리케이션이 Codex 로그인을 자동으로 수행하지는 않습니다. CLI가 없거나 로그인 상태가 유효하지 않으면 AI 기능만 사용할 수 없는 상태로 처리하고 일반 단어 검색, 메모, 관리자 기능은 계속 사용할 수 있게 합니다.

Windows의 npm 전역 설치에서는 `codex.cmd`, `codex.ps1`, `codex.exe` 중 하나가 PATH에서 발견될 수 있습니다. 서버는 `where.exe codex`로 PATH를 조회해 실제 `codex.exe`를 우선 실행합니다. 실제 실행 파일을 찾지 못하면 서버 전용 환경 변수 `CODEX_CLI_PATH`에 신뢰할 수 있는 실행 파일 절대 경로를 지정합니다. Linux에서는 기본적으로 `codex` 명령을 사용합니다.

Node.js에서는 `codex.exe` 또는 Linux의 `codex` 실행 파일을 `shell: false`로 직접 실행합니다. 사용자 입력은 명령 인자가 아닌 stdin으로 전달합니다.

### 17.5 서버 실행 구조

브라우저에서 Codex CLI를 직접 실행하지 않습니다. 전체 흐름은 다음과 같습니다.

```text
브라우저 폼
  → Server Action에서 Better Auth 세션과 입력값 검증
  → 서버 전용 AI 함수가 호스트의 codex exec 실행
  → JSON Schema에 맞는 결과 수신
  → 서버에서 결과 재검증
  → MongoDB 저장 또는 퀴즈 화면 반환
```

Next.js에서는 Node.js의 자식 프로세스(Child Process)를 이용해 비대화형 명령인 `codex exec`를 실행합니다. 실제 구현 파일은 브라우저 번들에 포함되지 않는 서버 전용 디렉토리에 두며 코드 흐름은 `page 또는 action → lib/ai → Codex CLI → 검증 → DB` 순서로 구성합니다.

사용자는 미리 정의된 **AI 단어 생성**과 **AI 퀴즈 생성**만 요청할 수 있습니다. 임의 프롬프트, CLI 옵션, 실행 디렉토리, 모델 권한을 브라우저에서 전달받는 범용 Codex 실행 API는 만들지 않습니다.

개념상 다음과 같은 명령을 사용합니다.

```text
codex exec --ephemeral --sandbox read-only --skip-git-repo-check --output-schema <schema-file> -
```

- `exec`: 대화형 화면 없이 서버 작업으로 실행합니다.
- `--ephemeral`: 실행 세션 기록을 호스트 디스크에 계속 보관하지 않습니다.
- `--sandbox read-only`: AI가 프로젝트 파일을 수정하지 못하게 합니다.
- `--output-schema`: 단어 또는 퀴즈 결과를 약속한 JSON 구조로 제한합니다.
- `--skip-git-repo-check`: 서버가 새로 만든 비밀 정보 없는 임시 작업 폴더에서만 Git 검사 생략을 허용합니다.
- `-`: 전체 프롬프트를 표준 입력(stdin)으로 받습니다.

사용자가 입력한 검색어를 쉘 명령 문자열에 이어 붙이지 않습니다. 서버가 고정된 CLI 인자만 만들고 검색어와 단어 데이터는 표준 입력으로 전달합니다. 이를 통해 검색어에 따옴표나 명령 문자가 포함되어도 운영체제 명령으로 해석되는 Command Injection 위험을 줄입니다.

Codex 프로세스의 표준 출력(stdout)에서는 최종 JSON만 읽고, 진행 정보와 오류가 출력되는 표준 오류(stderr)는 서버 로그로 분리합니다. 브라우저에는 내부 경로, CLI 인증 정보, 전체 프롬프트, 상세 오류 로그를 보내지 않습니다.

### 17.6 실행 환경 격리와 보안

Codex CLI는 코드를 다루는 에이전트이므로 일반 텍스트 생성 API보다 로컬 파일 접근 범위를 더 신중하게 제한해야 합니다.

- AI 요청은 프로젝트 루트나 `.env.local`이 있는 폴더에서 실행하지 않습니다.
- AI 전용의 비어 있는 작업 디렉토리를 사용하고 소스 코드와 비밀 정보를 넣지 않습니다.
- Codex에는 파일 쓰기 권한을 주지 않고 `read-only` sandbox만 사용합니다.
- `workspace-write`, `danger-full-access` 권한은 AI 단어와 퀴즈 생성에 사용하지 않습니다.
- 자식 프로세스에 `process.env` 전체를 전달하지 않고 PATH, 임시 폴더, Codex 인증 위치처럼 필요한 환경 변수만 허용합니다.
- `MONGODB_URI`, `BETTER_AUTH_SECRET`과 같은 애플리케이션 비밀 값은 Codex 자식 프로세스 환경에서 제외합니다.
- 사용자 검색어는 지시문이 아니라 데이터라는 점을 고정 프롬프트에 명시합니다.
- 사용자가 고정 프롬프트, JSON Schema, CLI 옵션을 변경할 수 없게 합니다.
- Codex 결과가 DB 명령을 직접 실행하게 하지 않고, 서버 코드가 검증된 값만 저장합니다.
- CLI 인증 파일이나 토큰을 프로젝트, MongoDB, Git 저장소에 복사하지 않습니다.
- 한 사용자의 중복 클릭과 과도한 동시 실행을 제한합니다.
- 실행 제한 시간을 넘기면 자식 프로세스를 종료하고 DB를 변경하지 않습니다.

Codex CLI는 기본적으로 Git 저장소에서 실행되는 도구입니다. AI 전용 작업 디렉토리는 비밀 정보가 없는 작은 Git 저장소로 준비하는 방식을 우선 사용합니다. `--skip-git-repo-check`가 필요하다면 격리된 디렉토리인지 확인한 뒤에만 사용합니다.

현재 Windows 개발 환경의 ChatGPT 로그인 정보는 Codex CLI가 호스트에서 관리합니다. Linux 배포에서도 웹 서버를 실행하는 전용 OS 사용자가 미리 로그인한 상태를 사용합니다. 인증 캐시 파일은 비밀번호처럼 취급하며 프로젝트 파일이나 배포 로그에 포함하지 않습니다.

공개 서비스에서는 사용자가 Codex 자체를 직접 조작할 수 있게 하지 않습니다. 로그인, 요청 횟수 제한, 고정 프롬프트, 읽기 전용 sandbox, 환경 변수 제한, 실행 시간 제한을 모두 통과한 두 가지 기능만 서버에서 실행합니다.

### 17.7 AI 결과 검증과 중복 방지

AI 출력은 올바른 사실이라고 가정하지 않고 다음 순서로 검사합니다.

1. Codex 프로세스가 정상 종료되었는지 확인합니다.
2. 출력이 JSON으로 변환되는지 확인합니다.
3. JSON Schema와 필수 필드를 확인합니다.
4. 문자열의 앞뒤 공백과 배열 값을 정리합니다.
5. category가 프로젝트의 6개 값 중 하나인지 확인합니다.
6. slug 형식과 tags 배열을 확인합니다.
7. AI 단어의 직역 의미, 설명, 코드 예시가 비어 있지 않은지 확인합니다.
8. codeLanguage가 `javascript`, `jsx`, `bash`, `text` 중 하나인지 확인합니다.
9. 저장 직전에 같은 slug가 이미 생성되었는지 다시 확인합니다.
10. 모든 검사를 통과한 경우에만 MongoDB에 저장합니다.

두 사용자가 같은 단어를 동시에 요청하면 두 Codex 실행이 시작될 수 있습니다. 최종 저장 단계에서는 `words.slug` 고유 인덱스가 중복 등록을 막습니다. 먼저 저장된 단어가 있으면 나중 요청은 오류로 끝내지 않고 이미 생성된 단어의 상세 화면으로 이동시킵니다.

AI 퀴즈도 문제 수가 3개인지, 각 단어가 현재 존재하는지, 정답 번호가 선택지 범위에 있는지 검사합니다. 브라우저가 보낸 점수는 신뢰하지 않고 서버가 사용자의 선택 답안을 다시 채점합니다.

### 17.8 실패 처리와 사용자 메시지

| 상황 | 사용자 메시지와 처리 |
| --- | --- |
| Codex CLI 없음 | AI 기능을 현재 사용할 수 없습니다. 일반 기능은 계속 제공 |
| Codex 로그인 만료 | AI 기능을 현재 사용할 수 없습니다. 서버 로그에 재로그인 필요 기록 |
| 실행 시간 초과 | AI 응답 시간이 초과되었습니다. 잠시 후 다시 시도해 주세요. |
| 잘못된 JSON 또는 검증 실패 | AI가 올바른 정보를 만들지 못했습니다. 다시 시도해 주세요. |
| 같은 단어가 먼저 등록됨 | 이미 등록된 단어의 상세 화면으로 이동 |
| AI 단어 저장 성공 | 단어가 생성되었습니다. |
| AI 퀴즈 생성 실패 | 퀴즈를 만들지 못했습니다. 다시 시도해 주세요. |

실패한 응답이나 일부 필드만 만들어진 응답은 MongoDB에 저장하지 않습니다. 자동 재시도는 같은 요청에서 한 번을 넘기지 않도록 제한하는 방식을 권장하며, 최종 횟수는 비용과 응답 시간을 측정한 뒤 확정합니다.

### 17.9 AI 데이터 관리

AI 단어는 기존 `words` 구조를 사용하며, 검증을 통과하면 즉시 공개합니다. AI가 직접 DB에 접근하지 않고 서버가 검증된 데이터만 저장합니다. 저장 이후에는 일반 단어와 동일하게 관리자가 수정하거나 삭제할 수 있습니다.

AI 퀴즈는 등록된 단어 데이터만 입력으로 사용합니다. 퀴즈 이력은 저장하지 않습니다. 채점에만 필요한 정답과 해설은 `quizSessions`에 최대 1시간 동안만 보관하고 제출 뒤 즉시 삭제합니다.

AI가 생성한 콘텐츠를 확정된 사실로 무조건 취급하지 않습니다. JSON Schema와 서버 검증을 통과한 경우에만 저장하며, AI 출처·모델 정보는 현재 단어 데이터에 저장하지 않습니다.

### 17.10 구현 결정값

AI 기능은 다음 값으로 구현합니다.

| 결정 항목 | 적용 값 |
| --- | --- |
| AI 단어 공개 시점 | 서버 검증 성공 후 즉시 `words`에 저장하고 공개 |
| AI 출처 필드 | 현재 추가하지 않음. 기존 단어 구조를 그대로 사용 |
| 기존 관리자 요청과 AI 요청 | 검색 결과가 없을 때 두 버튼을 함께 제공 |
| 퀴즈 선택지 개수 | 문제마다 중복 없는 선택지 4개 |
| 퀴즈 결과 시점 | 세 문제를 모두 제출한 뒤 점수·정답·해설을 한 번에 표시 |
| 퀴즈 내역 저장 | 이력은 저장하지 않음. 임시 세션은 제출 또는 1시간 뒤 삭제 |
| 퀴즈 재응시 | 제한 없이 가능하며 매번 새 문제 생성 |
| AI 일일 사용량 | 사용자별 AI 단어 요청 5회, AI 퀴즈 5회 |
| 실행 제한 시간 | 요청 한 번당 60초 |
| 동시 실행 수 | 사용자당 같은 기능 1개. 서버 전체 대기열은 현재 두지 않음 |
| Codex 모델 | 환경 변수로 강제하지 않고 호스트 Codex CLI의 기본 설정 사용 |
| Linux 배포 형태 | CLI와 자식 프로세스를 실행할 수 있는 장기 실행 VM 또는 컨테이너 |
| 운영 인증 방식 | 배포 전 전용 서비스 계정 또는 서버 전용 인증으로 확정 필요 |
| 관리자 퀴즈 관리 | 퀴즈 결과 이력이 없으므로 별도 관리 화면을 제공하지 않음 |
